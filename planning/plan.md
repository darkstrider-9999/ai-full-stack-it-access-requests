# Build plan

## Choices

- **Runtime:** Python 3.11, `uv` with `pyproject.toml` and `uv.lock`, and a pinned JSON Schema validator; this fits the class Python setup and makes dependencies reproducible. Select and lock exact package versions during implementation, not during this planning task. Use the supplied schema unchanged with an explicitly selected validator dialect.
- **Interface:** a CLI, provisionally `python3 -m access_intake`, backed by SQLite on one host; separate intake, queue, history, resume, retry, export and accuracy commands allow another operator to inspect committed results during intake.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`; all provider and HTTP boundaries are injected mocks, network use is forbidden, and tests never read `API_KEY`. Planned fixtures below do not exist yet; the starter canned reply is not an extraction fixture.
- **Model calls:** an injected provider interface with a deterministic file-backed mock first and a real HTTP adapter second. Proposed supported integration is OpenAI Responses API, with model ID, endpoint, timeout and output limit configurable; confirm the facilitator key's provider/model compatibility and consult that API's current official request/completion/refusal documentation before step 8. No live invocation is needed to build or verify this plan. The production-only credential loader reads `API_KEY`; adapter tests receive a dummy credential directly and test the loader through an injected environment lookup.

The following are proposed implementation choices, not additional business requirements. Shared operation supports two or more CLI processes on the same host and a local SQLite database, using short transactions, WAL, bounded workers (default 4), a busy timeout and durable attempt claims. Model calls occur outside database transactions. This does not promise multi-host/network-filesystem operation, a latency target, or exactly-once billing. Verify functional cases with small deterministic batches and a 2,000-message mock exercise; report measurements only after running it.

Store original source bytes, filename, 64-character lowercase SHA-256, immutable attempt IDs, configuration snapshots and policy hashes. Current pointers and immutable attempt/history rows are distinct. Processing states (`pending`, `running`, `succeeded`, `failed`, `interrupted`) are separate from policy statuses. Use database commit order at registration as a proposed revision ordering, with a generation check preventing stale completions from replacing newer attempts. Expose pending attempts alongside earlier results with explicit version labels. Export completed/latest failed attempts as one JSONL record and one queue-array entry per document; pending work is separately visible in the CLI. Export both files from one database snapshot into a generation directory and switch one generation pointer atomically; expose the required deliverable paths through that generation and document that consistent consumers pin a generation. Test the pair as well as the database; arbitrary readers opening the paths across a pointer switch must retry if generation IDs differ.

Reuse only the current successful result when source and extraction/routing fingerprints match. An unchanged failure stays visible until explicit retry. A retry names the attempt ID and replays archived bytes/settings, even if the source file has since changed; an obsolete retry remains historical. A changed source, including formatting-only bytes or A→B→A, gets a new revision. Relevant settings include provider endpoint/model, sampling/output options, prompt/schema and routing implementation/policy hashes; worker count is operational and does not invalidate results. Initially refresh by full extraction for policy changes as well as model changes; optimize routing-only refresh later only if tested. Retain history without automatic deletion. Use explicit operator retries, a configurable finite request timeout (proposed 60 seconds), and visible rate-limit/unavailability errors rather than hidden unlimited retry loops. Interrupted claims are reclaimed after their lease expires, with fencing against the previous worker; duplicate remote calls after interruption remain possible.

Successful records have `error=null`; failure records have `extraction=null` and a redacted error object with code, safe description, attempt ID and replay command. `response_source` is `mock` or a provider/model identifier; record attempted configuration separately when no response arrived and never imply an actual returned model was observed. Queue entries repeat attempt ID/hash, status/owner/action and link by document_id. Snapshot filenames, source bytes and history are retained outside current exports. Production credentials are excluded from prompts, database, history, evidence and logs.

## Steps, in build order

Each case ID below identifies a future test (parameterized rows count as one family). Each belongs to exactly one step. Steps 1–11 build the application; step 12 completes submission through manual checks rather than artificial application tests. For each step, write its named tests first, run them and record the missing behavior; only then implement until they pass and run the whole suite. Existing starter checks that already pass are recorded honestly, never broken deliberately. No step depends on a live provider call or `API_KEY`. This document authorizes no implementation, tests, commits, pushes or submissions now.
